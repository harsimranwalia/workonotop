# WorkOnTap Phase 1: handoff

This note says what Phase 1 covers, how each promise in the contract was checked, what could only be attempted in the development environment, and what you need to supply before the system can run for customers. The counts in section 3 were taken at **e529a5d 2026-10-17**; `git diff --stat e529a5d HEAD -- src database package.json playwright.config.js` prints nothing, and the files under `e2e/` that changed since are named in section 7. Any later change to the code makes the table in section 3 out of date; run the suite again (section 2) to refresh it.

Nothing described here ran against production. Production is not part of this build. The long form of this note is `HANDOFF-REFERENCE.md`; it was not checked line by line and may be out of date, and where it and the code differ the code is right.

## 1. What this is

Phase 1 is the quote-to-job core of the platform:

- A customer books online, one time or on a schedule, at the price the pricing rules produce.
- A job that cannot be priced becomes a quote request.
- A provider keeps a crew list and puts cleaners on a job.
- A cleaner whose number has passed its check types that number, is texted a six-digit code, enters it, and checks in everyone who showed up.

The contract lists twelve things by which "we'll know it worked", W1 to W12. Five of them are hard gates: W2, W5, W9, W11 and W12. The automated suite checks them: 1,994 cases in 72 files under `e2e/`. A map in `e2e/acceptance/contract.js` says which cases prove which sentence of the contract, and `npm run acceptance` reads a run of the suite against that map and says, for each item, whether the suite shows it.

## 2. Bring up the dev environment and run the suite

The development environment is two containers: an app container that runs the Next.js development server on port 3000 against the checkout, and a MySQL 8.4 container (host port 3307, database `workontap_db`) that holds 46 tables. The compose file and the development Dockerfile are not committed to the repository. The app container is named `workontap-app`. 36 of the 72 spec files reach the database themselves, and each spells out `127.0.0.1`, port 3307, user `root`, password `root123` and database `workontap_db`, with no setting to change them. The app connects on port 3306 and does not read `DB_PORT`: `grep -rn DB_PORT src` prints nothing. The fixture command runs in the app container and takes that container's `DB_HOST`: it refuses to run unless that is `db`, `localhost`, `127.0.0.1` or `::1` and the database is called `workontap_db`.

In order:

1. Install the packages in the checkout first (`npm ci --ignore-scripts`, then `node scripts/patch-ts-interface.cjs`): every machine that runs the suite needs them. Start the stack with the checkout mounted into the app container. On a Linux host where Docker runs as root the start leaves empty `node_modules` and `.next` folders in the checkout owned by root, and `npm ci` run as your own user then stops with `EACCES`.
2. Build the schema in the empty database. The suite needs 46 tables: the 33 of the live schema (a schema-only dump of the live database; the repository does not hold one) and the 13 that the eleven migrations in `database/migrations/` create. Load the live schema first, then apply the `.up.sql` files by hand, in the order that section 5 lists. `npm run db:init`, which runs `database/schema.js`, is not a substitute for the live schema. The suite has not been run against a database built from it.
3. Load the synthetic data, before a run and after it:

   ```
   docker exec workontap-app npm run db:fixtures
   ```
4. Tell the suite which variables the app has, run it, then read the run against the contract. The suite learns which credentials the app holds only from `E2E_APP_ENV_NAMES`, the comma-separated names of the variables the app has set. Without it, three cases are skipped instead of run, the journey case leaves out its approval step, and `npm run acceptance` reads W12 and W8 as NOT MET. One way to read the names from the app container:

   ```
   NAMES=$(docker exec workontap-app node -e 'const{combinedEnv:e}=require("@next/env").loadEnvConfig("/app",true,{info(){},error(){}});console.log(Object.keys(e).filter(k=>e[k]).join(","))') && export E2E_APP_ENV_NAMES="$NAMES"
   npm test
   npm run acceptance
   ```

   `npm test` is Playwright 1.58.2. On a machine with no browser build for that version, run the same command inside `mcr.microsoft.com/playwright:v1.58.2-noble` with the checkout and its `node_modules` mounted, `--network host`, `--ipc=host`, `--init`, `--user "$(id -u):$(id -g)"` and `-e E2E_APP_ENV_NAMES`, so that the suite reaches the app at `http://localhost:3000`.

If the stack or the fixtures are missing, the suite stops at the start and prints a line that says which. The two you will meet are:

- `app not reachable at <url> after <n> s (last: <problem>)`
- `fixtures not loaded in the database the app reads (fixture sign-in answered <status>); run the fixture command: npm run db:fixtures`

`npm test -- e2e/<file>.spec.js` runs one file; a full run is long (about an hour and twenty minutes in a later complete run), so it is easiest to run it in windows of a few files and to give the acceptance command the union: copy `test-results/baseline-candidate.json` to a folder outside `test-results/` after each window, merge the `cases` of the copies into one file of the same shape (a plain merge of the `cases` objects is what the gate reads) and pass it with `--results`. `npm run acceptance -- --markdown --label "<commit> <date>"` prints the tables in section 3. It exits 1 when a hard-gate item is not shown, or departs from the contract with no acceptance written into the map.

## 3. The twelve items

An item is the clauses of the contract's own sentence, and takes the status of its worst clause. The five count columns count clauses.

- **MET** (Live): requests to the running app and its database, or a real browser, show it.
- **MET (in-process)** (In process): the code that does it was run directly in the test and not through the running app. Where it calls an outside service (the card service), a stand-in took its place. D4 and D5 carry this label too, but all of their cases go through the running app.
- **ATTEMPT-ONLY** (Attempt only): the code was seen to try, and nothing was delivered. Section 4.
- **DEPARTS** (Departs): the build does something different from the contract's words. The difference is written in the map and waits for a decision (section 7).
- **NOT MET** (Not met): a case failed, was skipped (other than the two named below), was renamed or deleted, has no result, or ended `ATTEMPTED` in a clause the map does not declare attempt-only.

## 4. Verified only by what the code attempts

Some promises end at a service the development environment has no account with: Twilio (texts), an SMTP server (e-mail) and Stripe (the card). For these the suite shows that the code decides to send, to the right people, once, and that it records the attempt. It cannot show that the service delivers. A case that goes through the running app and notes that a credential it needs is missing reports `ATTEMPTED (missing: ...)`, never `PASS`, and the acceptance command prints a clause that the map declares attempt-only as ATTEMPT-ONLY while one of its cases ends `ATTEMPTED`, and counts it as met only when none does (which needs the credentials). A case that does not note it reads `PASS` even where the path it takes reaches a send or a charge.

**Texts and e-mails** (W3: the quote and card link; W4: the job link; W8: the alerts for an on-site report; W10: the seven kinds). A notice claims a row in `notice_attempts` before anything is sent: one row for one person, one message and one channel. With no Twilio or SMTP credential the row ends `not_configured`. The code also texts the customer when a job is started or finished from the provider's page, two notices the contract does not list. Of the 1,994 cases, 31 end `ATTEMPTED`, and `e2e/baseline.json` lists them.

**The card held, not charged** (W1). With no Stripe secret key, a booking made outside production is recorded as `pending` and the completion cannot charge it (`booking-payment.spec.js`). The case that asks the payment-intent route for a hold (`harness.spec.js`) ends `ATTEMPTED`: with no key the route cannot start a payment and answers 500. What the suite does not show is Stripe accepting the hold.

**What would turn them into passes.** For the texts and the e-mail: the three Twilio variables and an SMTP account, and the list of variable names that section 2 has you set in `E2E_APP_ENV_NAMES`. With a secret key in the app, the booking route wants a payment that was held for the account the booking is recorded for, and answers 400 ("This payment does not match this booking.") both for a payment held for any other account and for a booking recorded for no account, before it asks Stripe; the suite's checkout posts are guest bookings, so a real test-mode payment id alone does not make them pass. The case (`job-reports.spec.js`) skips itself once `STRIPE_SECRET_KEY` is in the list, and the acceptance command counts a skipped case that the map does not name as a gap against W8. The `stripe-complete` case in `ownership.spec.js` skips itself the same way and the map takes that whole file for W12, so the acceptance command would then read W12, a hard gate, as NOT MET. All of this is read from the cases; the suite has not been run in that state. Run it with test credentials before relying on it, expect these cases to need attention.

## 5. What you must supply before production

- **Stripe.** A live secret key (`STRIPE_SECRET_KEY`), the publishable key (`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`) and the signing secret for Stripe's webhook (`STRIPE_WEBHOOK_SECRET`). The webhook route writes the whole request body and the request's headers to the application log before it checks the signature, and the first eight and last four characters of the signing secret as well. **Without a secret key** the payment step (`/api/payment/create-intent`) answers 500, so a customer cannot book. An admin's booking on a customer's behalf holds no payment; the card the customer then puts on file from the link needs both Stripe keys. The card-saving terms are yours and your lawyer's: the build supplies none. It does show one line of consent wording on the confirm and payment steps of a booking that repeats (`src/components/booking/SeriesConsent.jsx`), which you and your lawyer should approve or replace.
- **Twilio.** `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_PHONE_NUMBER`, a number approved to text Canadian numbers, and a spend limit or usage alert in the Twilio account. The code bounds what it spends: 8 texts a day to one number, 200 a day for one provider and 500 a day for the platform. In a production deploy `NEXT_PUBLIC_APP_URL` must be the real `https:` address of the site (so leave the slash off): with anything else, unset included, the card link and the job link are not sent (`no_origin`) and other notices go without their link. It must also be no longer than 31 characters with its `https://` (counted as the code works the address out with `new URL()`: a trailing slash or `:443` is not counted, and a host name with accented letters counts in its `xn--` form): from 32 characters the card link is not sent, and from 33 the job link is not sent either, each recorded as `error`.
- **E-mail.** `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` and `EMAIL_FROM`, and `ADMIN_EMAIL`. Set `ADMIN_EMAIL` to one plain address (`ops@example.com`): the on-site report notice refuses a value with a comma, a display name or angle brackets (`bad_contact`) and sends nothing to it, while the four older mails hand the value to the mail library as it stands. The one about a provider's sign-up and the one at the end of onboarding go only to `ADMIN_EMAIL`, and where it is unset to a personal address written into the code; the one about a dispute and the one about a payment that could not be taken go to `ADMIN_EMAIL`, else to `NEXT_PUBLIC_ADMIN_EMAIL`; so set `ADMIN_EMAIL` before launch. The connection is opened in plain text and upgraded by STARTTLS when the server offers it; a mail provider that offers only port 465 will not connect without a change to the code.
- **Secrets.** `JWT_SECRET` has no built-in value: with it unset every customer and admin sign-in answers 500. `CRON_SECRET` is needed by the three scheduled jobs in `vercel.json`; they refuse to run without it. A customer's or a provider's own account is anonymised by `scripts/cleanup-deleted-accounts.js`, which nothing in the repository schedules and which cannot be run as it stands. `AI_GATEWAY_SECRET_KEY` guards the routes under `/api/ai-gateway/v1`; the placeholder in the example file, `generate-a-secure-random-token-here`, works as the key if it is copied as it stands. The database login falls back without a message to host `localhost`, user `root`, password `root123` and database `workontap_db` for each of `DB_HOST`, `DB_USER`, `DB_PASSWORD` and `DB_NAME` that is unset. The code names 37 variables: `grep -rhoE 'process\.env\.[A-Za-z_0-9]+' src | sort -u` prints them.
- **Other names the code reads.** This list is starting points, not a complete one. `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`. `NEXT_PUBLIC_BASE_URL` (the sitemap, `robots.txt`, `llms.txt` and the AI gateway's OpenAPI file; unset, all four name `https://workontap.com`, so a staging site that leaves it unset publishes the live site's address). Write it as `https://` and the host with no trailing slash: it goes straight in front of each path. `JWT_EXPIRES_IN` (how long the token of a provider's password sign-in on the web lasts, 7 days by default). It must carry its unit (`7d`, `12h`): a bare number such as `3600` is read as milliseconds, so the provider's token is dead long before the 7-day cookie, and a value the library cannot read makes every provider password sign-in on the web answer 500. Every `NEXT_PUBLIC_` value, including `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` and `NEXT_PUBLIC_APP_URL`, is fixed when the site is built: set them before the build.
- **Where photos live.** A production store for photos is **not chosen**. The host (Vercel) has no persistent disk, so photo capture works only where there is a disk. The choices are an object-storage vendor or the database. Photos from a job link are written and deleted by one file, `src/lib/job-photo-store.js`. A photo taken from a job link has a random 128-bit name, which is its only protection: anyone who has the address can read it. The daily clean-up deletes the photo after 365 days, except while its booking is `disputed`. Every other file that goes through `/api/upload` is named with the time in milliseconds and the name of the file it came from, which can be guessed, and is kept until someone deletes it. If a store is on another origin, the content security policy must name it in `img-src`.
- **Hosting.** The texts and e-mails of the nine kinds of notice are sent after the response is returned, by Next's `after()`, so the host must keep the process alive until they finish. The job link page and the card link page, run none of the site-wide scripts; make sure nothing at the host or a proxy adds a script to `/job/*` or `/card/*`. Confirm that the application server and the database agree on the time zone.
- **The database.** The changes are plain SQL in `database/migrations/`, applied by hand, in this order: `0001` service pricing items, `0002` payment intent unique, `0003` marketplace pushed at, `0004` visit series, `0005` quote requests, `0006` booking card links, `0007` provider crew, `0008` job links, `0009` job photos and timer, `0010` job reports, `0011` notice attempts. Each has a `.down.sql`. Before `0002`, run the query in its header: if it returns rows, stop. Deploy the code after the migrations, with the Stripe key set, and then enter the pricing rules. A service's rule is its catalog price and duration plus rows of the table `service_pricing_items`. No page and no route writes that table, so the rows are entered in SQL. The development data holds invented figures marked `is_placeholder = 1`, and the client's own figures are rows with it set to 0. The percent off a booking that repeats is three keys of `system_settings`, `recurring_discount_weekly_percent`, `recurring_discount_every_2_weeks_percent` and `recurring_discount_monthly_percent`. An admin sets these by posting a `key` and a `value` to `/api/admin/settings`.
- **One question.** Does the table `user_addresses` exist in production? The address routes (`/api/user/addresses` and `/api/user/addresses/{id}`) answer 500 without it. The development database does not have it, and no file in the repository creates it: not `database/schema.js`, not `database/schema.sql`, not a migration.

## 6. What is deliberately not built

The contract's own out-of-scope list (the contract is not in the repository, so this list could not be checked against it here): extension approvals, contractor staff logins, mobile app changes, a live dashboard, refund and dispute flows, double-charge protection, new revenue features. Double-charge protection is not a feature of its own, but the main charges and payouts are made under a key built from the booking (or the report), so a repeat of the same request within Stripe's 24-hour memory of the key returns the first and is not a second charge. The money an admin moves when resolving a dispute, the payout the Stripe webhook makes after an overtime payment, and the hold taken at checkout carry no such key.

Knowingly left, in plain words:

- A production store for photos (section 5); a control for an admin to delete one job photo, and a way for a customer to ask for one to be deleted.
- A way to correct a check-in made by mistake; hardening of the link's check-out and the timer.
- A page where a customer approves or disputes an added-items charge before it is made. No customer has one, with an account or without.
- Older code, outside this work: a provider who has signed up and not been approved, or who has been suspended, can sign in once their e-mail is verified (a rejected provider is refused at the web sign-in; the app's sign-in does not look at that status, so a rejected provider whose e-mail was verified can still sign in there and use the same routes) and use the provider routes; the admin's Jobs list is the newest 50 jobs whose contact e-mail belongs to an account; a job whose e-mail has no account is not in it until an account with that e-mail is made. The admin's route that updates a dispute (`PATCH /api/admin/disputes`) reads three names that it never takes from the request, so it stops with a 500 for every dispute that exists and the screen cannot resolve one (found by reading the code and not run). The public checkout writes the customer's contact to the application log.

## 7. Known gaps in the evidence

- **The provider's "Start Job" button (W5).** Decision asked of you: close the second door, or accept it in writing. Closing it means changing the provider's page to open the job link, where the provider may start the job, and making the time-tracking route refuse a start. (a) The text to the customer that the job has started is sent only by the provider's route today; the job link sends none. (b) The cases that pin the open door turn red until they start from the link. (c) A job link can only be made for a job with a cleaner on its crew, so a provider who works without a crew list could no longer start a job. (d) The mobile app starts a job through the same route and has no screen for the job link, so refusing a start there stops every start from the app until the app is changed; no case in the suite covers the app. Closing the door also means taking `W5.one-door` out of the map as a departure (or the gate keeps printing DEPARTS and exits 1), rewriting the case AC2 of `job-timer.spec.js` and the case "W5.one-door" of `acceptance-links.spec.js` to pin the refusal, and rewriting the three drills in `acceptance-gate.spec.js` that need that clause to be a departure; `npm run acceptance` exits 1 on W5 until the clause is accepted or taken out of the map. Accepting it means filling in `accepted` on `W5.one-door` in `e2e/acceptance/contract.js` with `by`, `on` and `ref`, all three as text (who accepted, when, and where it is written down). Anything else makes the map invalid, and `npm run acceptance` then stops with exit code 3 and says why.
- **Two cases skipped by name.** Two cases in `ownership.spec.js` cannot be observed because the development database has no `user_addresses` table.
- **Four findings, not fixed.** (a) `GET /api/provider/available-jobs/{id}` returns the street and the instructions of a job on the marketplace to a provider of any status (active, pending, inactive and suspended all got an answer), where the list of open jobs hides the street until the provider has the job. (b) `POST /api/provider/signup` is public and e-mails whatever address is typed; one signup per address is the only limit, so the form can be used to send mail to other people's addresses. (c) `POST /api/upload` takes a file from any signed-in customer, provider or admin and checks only that the type the sender names starts with `image/`. A file called `something.svg` is stored as sent and served as `image/svg+xml`. An SVG can carry script, so a signed-in customer can put up a page that runs script as the site, for whoever is sent its address. Refusing a file whose name ends in `.svg` (and keeping to an allow-list of extensions, not only the type the sender names), or serving every upload with `Content-Disposition: attachment` from every path that serves `/uploads/`, would close it; either is a change to `src/`, so a full run of the suite again. (d) When the platform's 500 texts a day are used up, a cleaner's request for a sign-in code at a job link answers 500 ("Failed to send the code") and not the usual answer. All four were found by reading the code, and (a) and (c) were also measured on the development environment; none is one of the nine defects.
- **The label.** The table in section 3 describes the commit named at the top. Six files under `e2e/` have changed since that commit, and each was run again afterwards: `acceptance/gate.js`, `acceptance-gate.spec.js`, `acceptance-links.spec.js`, `acceptance-journey.spec.js`, `acceptance/contract.js` and `claim-status.spec.js`. All 1,994 cases on this tree read PASS 1,961, ATTEMPTED 31, SKIPPED 2, FAIL 0, every outcome equal to the baseline's, and the gate prints the table in section 3 over them. That is not one uninterrupted run: it is put together from runs in windows, the files that changed after the last complete run having been run again on this tree and the results of the others carried over from that run.
